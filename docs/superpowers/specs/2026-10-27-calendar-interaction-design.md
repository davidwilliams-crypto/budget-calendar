# Month fit, readable payments, moving transactions, and balance editing

Implement the user's explicit request in the existing Rust desktop app. Every date and daily balance in four-, five-, and six-week months must fit the available calendar area without calendar scrolling, including a 900x600 window. Payment names get the full row width, stronger readable type, and amounts beneath when space permits. Crowded days expose every transaction in the existing day dialog through a count control; never hide the daily balance or allocate a taller-than-available grid.

Dragging a calendar payment moves the selected occurrence to another date. Preserve amount, notes, paid/important status, highlighting, unrelated occurrences and schedule exceptions. Use typed drag payloads with stable payment IDs. Highlight the destination and show a drag preview. Dropping outside the calendar or on the same date does nothing. Reject a destination that already contains that payment instead of silently overwriting it. Allow adjacent-month day drops and forward/backward month navigation while dragging. A move stays unsaved until normal Save, using existing backup/conflict protections.

Right-click a daily closing balance and choose Edit balance. Seed an amount dialog with the exact balance, show the date and effect, reject non-finite/invalid values without mutation, and apply a dated balance adjustment. Optionally remove an existing adjustment through the same dialog. Subsequent balances update up to the next existing adjustment; payment amounts, notes, and other adjustment metadata remain unchanged. Opening/closing summary cards also offer the matching balance edit action using the previous month's last day/current month's last day respectively.

Preserve existing budget format, safe saves, dirty/draft close guards, editing and filtering. Verify actual drag/drop and balance editing on a private budget copy, full-month native renders and bounded geometry at compact/standard sizes, round trips and cancellation/error cases, independent review, final build and launch through the existing app path. Never write the original budget as test data.

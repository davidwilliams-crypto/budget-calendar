# Budget Calendar development and local releases

Preserve the user's budget files and any open, unsaved work. Use generated fixtures under `target/` for tests. Never use, alter, overwrite or archive the user's `.bgt` files as test data. Do not close an open application draft to replace its executable; build and archive a new executable while leaving the running application alone.

For every delivered application change:

1. Increment the semantic version in `budget-gui/Cargo.toml` and update the matching `budget-gui` entry in `Cargo.lock`. The GUI package version is the version source. Never reuse a published version for a changed executable or build identity.
2. Add a `## [VERSION] - YYYY-MM-DD` entry to `CHANGELOG.md` describing the resulting user-visible changes. Keep prior release entries intact. Version 0.3.0 is the first tracked local release; earlier local updates shared the imported 0.2.0 label and must not be assigned invented releases.
3. Run the relevant regression checks, then the release gate: `powershell -NoProfile -ExecutionPolicy Bypass -File scripts/release-gate.ps1`. It is the single pass/fail for the workspace tests, build-fingerprint tests, native/WASM parity, all mobile unit and browser tests, the three-client integration test, every `scripts/tests/*.Tests.ps1`, and the check that `budget-mobile/public/budget_engine.wasm` matches its Rust sources (run `scripts/build-mobile.ps1` when it does not). A release needs a clean pass: `-AllowSkip` is only for local work, and a skipped step means that area was not tested. CI runs the same gate from `.github/workflows/ci.yml`. Build the release executable. Use the configured local Rust toolchain and offline Cargo cache where required by the environment. Confirm `budget-gui.exe --version` and `budget-gui.exe --version-json` report the intended version without opening a GUI or loading a budget.
4. After all release sources are final, run `scripts/tests/archive-release.Tests.ps1`, rebuild if those sources changed, and run `scripts/archive-release.ps1` to archive `target/release/budget-gui.exe` into `local-releases/vVERSION`. The build-generated input manifest must match the executable and the current source. The archive contains the executable, icon, changelog, build input manifest, matching source ZIP and `release.json` with build identity and SHA256 checksums.
5. Report the delivered version, build identifier, test/build results and archive path. A repeated archive of the identical build is safe; a version collision must be resolved by incrementing the version and building again, never by deleting or overwriting the prior release.

The archive accepts `-ExecutablePath`, `-OutputDirectory` and `-BuildManifestPath` for a previously built executable and its build-generated manifest. All paths must stay inside this repository. Defaults use `target/release/budget-gui.exe`, `local-releases/` and the matching `target/release/build/budget-gui-*/out/build-inputs-BUILD_ID.json`. Do not archive `.git/`, `target/`, `local-releases/`, `reference/`, `analysis/`, user budgets, credentials or secrets. The source inventory is an explicit allowlist of application/core/vendor code, assets, manifests, the lockfile and release workflow files.
